# HK ELI Chatbot on Dify: what was built, how it was tested, what we found

\*Will be part of Ask-MIRA in future

Date: 24 Nov 2026. Branch `claude/project-thread-aibrnw` of repos-3sds/hk-eli, draft PR #26.
Runs 1 to 3 used the fictional mock workbook. Run 4 used Hawk's Tableau Cloud trial, which holds the same
fictional HK_ELI workbook (synthetic data). No keys or secrets appear in this file.

## 1. Why

Our direction changed on 24 Nov 2026 from the Stork API to Dify. The agreed flow is: the UI sends a question,
Python assembles the initial context, Dify processes, fetches (through Python) and streams, and Python grades
and reflects. The bank's UAT stack: Web Components with Polymer Lit in Digimarkets, a Java + Spring Boot backend,
Python + Flask AI services, Elasticsearch, Enterprise ELK, ENAAS secrets, and Tableau dashboards moving to TMTB
over Connected Apps Direct Trust.

Hawk asked for a Dify Chatflow first. After seeing it, Hawk asked for a Dify **Agent** app too ("intelligent
agent with reasoning and autonomous tool use"), with our code doing the context engineering and MCP tools the
agent may call. Then Hawk asked us to compare the two, and chose **"Keep both, fix both"**.

## 2. The rules both apps keep

- Figures come from data. Code picks the Tableau view, filters and figures; the model only reads the question
  and writes the words.
- Python checks every figure in the final text against what Tableau returned. A failed check gets one rewrite,
  then the plain template answer.
- Refusals (advice, forecasts) are made by code before any model runs.
- Dify and Gemini never see client or position ids (masked), Tableau credentials or full row sets.
- Tableau is reached only from Python, signed in as the asking user (Connected Apps JWT), so row-level security
  applies. Dify has no route to Tableau.

## 3. App 1: the Chatflow ("HK ELI Chatbot", Dify advanced-chat)

A fixed graph. File: `poc/dify/hk-eli-chat.yml`, generated by `poc/dify/build_dsl.py`.

```
Start (request_id, mode)
 └ Mode? ── reword ─> Reword (HTTP) > Read reword > Word (LLM) > Answer (rewrite)
    └ answer ─> Context (HTTP) > Read context > Needs model?
                  ├ yes > Understand (LLM) ┐
                  └ no  > No model ────────┴> Model text > Answer from data (HTTP) > Read answer > Wordable?
                                                              ├ yes > Word (LLM) > Answer (worded)
                                                              └ no  > Answer (headline)
```

1. **Python context** (`flow/context.py`): rules read the question; if they are unsure, Python renders the
   `understand` prompt. Dify gets prompts and flags only.
2. **Dify**: runs Understand (Gemini) only when the rules are unsure, then calls `POST /tools/answer`. Python
   fetches from Tableau as the user, validates and composes, and returns the `write_answer` prompt with ids
   masked. Dify's Word step (Gemini) writes the text and streams it.
3. **Python grade and reflect** (`flow/grade.py`, `flow/run.py`): checks figures, banned phrases and result
   labels. On failure, Python calls Dify again with `mode=reword` (one rewrite), then keeps the template.

The widget sees stage events (Assemble, Context, Understand, Answer from data, Word, Grade), a `token` event with
the draft headline marked "checking", then the graded answer, which replaces the draft.

## 4. App 2: the Agent ("HK ELI Agent", Dify agent-chat, function calling)

File: `poc/dify/hk-eli-agent.yml`.

1. **Context engineering in code** (`flow/agentic.py`): before Dify is called, Python reads the question, picks
   the view and filters, fetches as the user, checks the figures and builds a **context pack**: figures, up to
   10 masked rows, scope, data date, caveats, the template answer, and (for vague questions) the possible
   readings.
2. **Dify Agent**: gets the question plus the pack. It answers from the pack, or calls our **MCP tools** when it
   needs more:
   - `eli_ask(question)`: another data question, answered by code from the views as the same user (at most 4).
   - `eli_views()`: which views exist and what each covers.
3. **Python grade**: the agent's text is checked against every figure it was given (the pack plus each tool
   result), plus banned phrases and result labels. On failure, one rewrite in the same conversation, then the
   template answer.

Refusals and empty results never reach the agent. A question the rules read several ways goes to the agent
with its readings; the agent fetches one with `eli_ask` and says which ("Read as: ...").

MCP server: `POST /mcp` on the Python service (Streamable HTTP, JSON replies), bearer `DIFY_TOOL_KEY`.

## 6. How it was tested

### Automated (cloud, every commit): 316 tests pass

- **Parity**: the Chatflow (run in-process by `LocalDify`) gives the same answer as the native pipeline on the
  24-question eval set, the full intent bench and the held-out set, with the model off and with a fake model.
- **Reflect**: an invented figure gets one rewrite and passes; two failures keep the template; empty model text
  keeps the template without a rewrite; Dify's "partial-succeeded" (a model step failed) keeps the template
  instead of an error.
- **Privacy**: id columns are masked in everything Dify sees.
- **Streaming**: event order (stage, token, answer), each stage shown once, SSE parsing of Dify events.
- **Agent**: answers from the pack pass; MCP tool use and its figures pass; invented figures get a rewrite;
  refusals never reach the agent; tool calls capped and tied to a live request; vague questions resolved by
  fetching a reading; maturities called knock-outs caught.
- **MCP protocol over HTTP**: initialize, notifications (202), tools/list, tools/call, auth (401), unknown
  method, GET 405.
- **Importable files**: both YAML files are current and parse to the generator's output (checked with PyYAML);
  the Chatflow graph is sound (every node reachable, every path ends in an Answer, every variable exists).

### Live on the Mac mini (local Dify 1.16.1)

Set up, each step approved by Hawk:
1. Started Dify in `~/Documents/dify/docker` (15 containers healthy).
2. Ran a second copy of our agent on **:8051** from the worktree `~/Documents/hk-eli-dify` (the :8050 and :4210
   apps were left untouched).
3. Dify's SSRF proxy: allowed only `host.docker.internal` port 8051 (backup `squid.conf.template.bak-2026-11-24`).
4. Dify `SSRF_DEFAULT_READ_TIME_OUT` 5 s → 60 s (backup `.env.bak-2026-11-24`).
5. Imported both apps; set `ELI_TOOL_BASE_URL` and `ELI_TOOL_KEY`; added the MCP server "HK ELI tools"
   (identifier `hk-eli`) and attached both tools to the Agent.
6. Created a Service API key for each app, saved on the Mac in owner-only files (`.dify_api_key`,
   `.dify_agent_api_key`, `.dify_tool_key` in `~/Documents/hk-eli-dify`).
7. Hawk pasted a working Gemini key into Dify. Gemini 2.5 Flash is closed to new keys, so both apps use
   **Gemini 3.5 Flash**.

Then `scripts/compare_dify.py` ran 8 questions through both apps, three times, fixing what each run found.

### What the comparison shows

- **Agent**: faster when the context pack covers the question (about 4 to 5 s against 6 to 8 s), tighter
  wording, and better on vague questions because it fetches more by itself. Slower (12 to 17 s) when it calls
  tools or needs a rewrite.
- **Chatflow**: the same path every time, easier to audit, never calls more than it needs, but thinner on vague
  questions.
- In both, code still decides the view, filters and figures, and Python checks every number.

## 8. Things learned on the way

- A Dify run whose model step fails ends as "partial-succeeded". We now keep the template answer instead of
  showing "service not reachable".
- Dify's SSRF proxy blocks private hosts by default, and its 5-second read timeout is shorter than our answer
  step.
- Dify 1.16 labels agent-chat "Legacy Agent". The new **Agents** type (beta) is called the same way and supports
  MCP, memory, versions and use as a Workflow step. But it passes only the prompt and the question to the model
  (our context pack would have to go inside the question), and it has a command shell on by default. We stayed
  on agent-chat for now; the new type is the likely long-term path for Ask-MIRA.
- Follow-up questions (multi-turn) aren't wired yet: Python should keep the last view and filters per
  conversation, and the Understand step should see the last few turns.

## 9. Still open

1. **Top N clients across the whole book**: no view ranks clients by total notional. Needs a new Tableau
   worksheet (proposed ask W9).
2. Chatflow on vague questions: suggest follow-up questions.
3. Chatflow on "knock out this week": sometimes answers, sometimes asks, and on the trial data it labelled all
   7-day maturities as knock-outs. Tighten the result-label check and make the rules consistent.
4. Follow-up questions across turns (see 8).
5. Trial workbook gaps (what-if only): add "Predictive Result" to the two outstanding-simulation views and
   publish `ALL_position_scenario`.
6. For the bank: port the tool service to Flask, the store to Elasticsearch, secrets to ENAAS, and the widget to
   Lit; agree where Dify runs, which Gemini route it uses, and the firewall from Python to Tableau (TMTB).
